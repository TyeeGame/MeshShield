# Hardware compatibility audit

Checked against official documentation and the **v1.5.2 tag** before implementing hardware code. Both projects target Device OS **1.5.2**. This is an obsolete demo target, not a recommendation for a production deployment. The Particle CLI and ARM toolchain were absent in the implementation environment; **neither Particle firmware project has been compiled or flashed here**. Native C++ tests validate only the portable protocol/policy/parser, not Device OS integration. No physical hardware validation has been performed.

| Requirement | Evidence | Implementation / qualification |
|---|---|---|
| Standalone, unconfigured Xenon | [Particle Xenon standalone archive](https://docs.particle.io/archives/xenon-standalone/); [Xenon support ceiling](https://docs.particle.io/xenon/) | `SYSTEM_MODE(MANUAL)`; no network/cloud calls. Xenon ceiling is 1.5.2. Install compatible bootloader, SoftDevice, and system firmware over USB before running the application. |
| Xenon I²C peripheral callbacks | [v1.5.2 nRF52840 I²C HAL](https://github.com/particle-iot/device-os/blob/v1.5.2/hal/src/nRF52840/i2c_hal.cpp), TWIS `READ_REQ`/`WRITE_DONE`, `HAL_I2C_Begin`; [callback restrictions](https://docs.particle.io/reference/device-os/api/wire-i2c/onrequest/) | `Wire.begin(0x21/0x22)`, `onRequest(void())`, `onReceive(void(int))`. Read callback copies an already prepared 18-byte packet. Receive callback only drains up to 32 bytes; this demo does not send Xenon controls. No allocation, logging, sensor reads, or scheduling in callbacks. |
| Two distinct Argon controllers and pins | [official pin mapping](https://docs.particle.io/reference/device-os/api/wire-i2c/pins-i2c/); [v1.5.2 HAL mapping](https://github.com/particle-iot/device-os/blob/v1.5.2/hal/src/nRF52840/i2c_hal.cpp#L100) | `Wire`: SDA D0/SCL D1; `Wire1`: SDA D2/SCL D3. HAL uses separate TWIM/TWIS instances. Each bus is independent. |
| Explicit transaction timeout | [requestFrom, introduced 1.5.0](https://docs.particle.io/reference/device-os/api/wire-i2c/requestfrom/); [v1.5.2 header](https://github.com/particle-iot/device-os/blob/v1.5.2/wiring/inc/spark_wiring_i2c.h); [HAL request implementation](https://github.com/particle-iot/device-os/blob/v1.5.2/hal/src/nRF52840/i2c_hal.cpp#L371) | `WireTransmission(address).quantity(18).timeout(uint32_t(5))`. Uses the verified integer-millisecond overload, not a later `setTimeout` API. |
| Timeout caveat | [v1.5.2 HAL reset](https://github.com/particle-iot/device-os/blob/v1.5.2/hal/src/nRF52840/i2c_hal.cpp#L543) | Error/timeout calls `HAL_I2C_Reset`: nine 200 µs pulses plus **50 ms delay**. Thus 5 ms is a transfer-wait limit, **not** a total wall-time limit. Typical worst error path is about 57 ms plus scheduling/driver overhead. Failed node gets 250 ms backoff; other node still gets its turn. Healthy polls target 20 ms. No hard real-time guarantee is claimed. Physical stuck-bus testing remains required. |
| USB serial without blocking | [v1.5.2 USBSerial source](https://github.com/particle-iot/device-os/blob/v1.5.2/wiring/src/spark_wiring_usbserial.cpp); [v1.5.2 nRF USB HAL](https://github.com/particle-iot/device-os/blob/v1.5.2/hal/src/nRF52840/usb_hal.cpp) | `begin(115200)`, `blockOnOverrun(false)`, `isConnected()`, `availableForWrite()`. App owns six bounded transmit frames and writes at most 128 available bytes per loop. Does not call `flush()` or wait for a host. Source is more precise than current prose about dropped/overwritten bytes. |
| RGB | [v1.5.2 RGB header](https://github.com/particle-iot/device-os/blob/v1.5.2/wiring/inc/spark_wiring_rgb.h) | Verified `control`, `brightness`, `color` overloads. Local mode/status only; dashboard remains authoritative. |
| Session identifier | [v1.5.2 RNG header](https://github.com/particle-iot/device-os/blob/v1.5.2/hal/inc/rng_hal.h) | Boot-time hardware RNG value (`HAL_RNG_GetRandomNumber`, remap zero to 1). A random 32-bit correlation identifier, not authentication or a guarantee against collisions. Linkage still requires the real firmware compile. |

The proposed transport is supported at the source/API level; no alternate transport was invented. If hardware tests expose a driver failure, first confirm pull-ups, common ground, correct Device OS system parts, and one peripheral per bus. The smallest wiring fallback for a failed second controller is a **single shared Wire bus** with addresses 0x21 and 0x22, but it sacrifices stuck-bus isolation and is not implemented or represented as meeting the two-independent-bus requirement. Retain two buses for this demo.

Current Particle documentation can describe newer releases. API decisions above are grounded in the 1.5.2 source, not merely in modern examples. Compiling with that target and physically testing remains the final compatibility gate.
